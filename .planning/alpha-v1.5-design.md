## Problem Statement

Three parallel features targeting Backroad's next alpha milestone:

1. **Authentication (opt-in)** — let Backroad app developers gate their apps or personalize content using better-auth, without breaking the top-to-bottom script model
2. **llms.txt + Copy as Markdown** — make the docs site first-class for AI tooling consumers (Cursor, Claude Projects) who want to generate correct Backroad code
3. **Playwright E2E** — use the example app as a living test harness that covers all components and runs in CI

---

## What Makes This Cool

- Auth follows Streamlit's proven model exactly — developer owns the UI, Backroad owns the plumbing. Zero magic, zero surprise.
- llms.txt is framed correctly: it's not "SEO for LLMs" (which doesn't work), it's structured markdown for developers using AI tooling. That's Backroad's actual audience.
- Playwright E2E doubles as a component showcase and a regression safety net — the example app gets upgraded to cover everything, and tests prevent silent regressions as the framework evolves.

---

## Premises (all agreed)

1. **Auth is opt-in via config** — auth config lives in `run()` options, zero impact on scripts that don't need it. Exposes `br.user`, `br.login()`, `br.logout()` when enabled.
2. **llms.txt is for tooling consumers, not crawlers** — framed as a developer productivity feature. No major LLM provider passively reads llms.txt; the value is for humans using Cursor/Claude Projects.
3. **E2E, not component testing** — Playwright `webServer` fixture + project dependencies is the right pattern for a WebSocket-based app. Playwright component testing is Vite-sandboxed and explicitly doesn't support WebSockets.

## Feature 1: Authentication via better-auth

### API Design

Developer experience mirrors Streamlit's `st.user` / `st.login()` pattern:

```ts
import { betterAuth } from 'better-auth';
import { run } from '@backroad/backroad';

run(
  (br) => {
    if (!br.user.isLoggedIn) {
      br.write({ body: '## Please log in to continue' });
      br.button({ label: 'Log in with Google', onClick: () => br.login() });
      return;
    }

    br.write({ body: `# Hello, ${br.user.name}!` });
    br.button({ label: 'Log out', onClick: () => br.logout() });

    // rest of app...
  },
  {
    auth: {
      instance: betterAuth({
        database: /* user's DB adapter */,
        socialProviders: {
          google: {
            clientId: process.env.GOOGLE_CLIENT_ID!,
            clientSecret: process.env.GOOGLE_CLIENT_SECRET!,
          },
        },
      }),
    },
  }
);
```

### What Backroad does internally

- Detects `config.auth.instance` at server startup
- Mounts `toNodeHandler(auth.instance)` on `GET|POST /api/auth/*` **before** any other middleware (critical — `express.json()` must not run first)
- Resolves the current session at WebSocket handshake time from the HTTP upgrade request headers (`auth.instance.api.getSession(upgradeRequest)`), then stores it in memory indexed by connection ID for the lifetime of that WS connection
- Exposes the session as `br.user` — a discriminated union (see type below)
- `br.login(provider?)` — triggers client-side redirect to `/api/auth/signin/{provider}`
- `br.logout()` — triggers client-side call to `/api/auth/signout`

**WebSocket session flow:** Backroad is WS-based, not request/response. The session cookie travels in the HTTP upgrade request headers. On WS connection open, Backroad calls `auth.instance.api.getSession()` once with the upgrade request, stores the result, and passes it as `br.user` on every subsequent script execution cycle for that connection. Session is not re-checked per-message (v1 limitation — document this). Pre-spike required: verify `getSession()` accepts a Node.js `IncomingMessage` (upgrade request) rather than a Web API `Request` object; if not, extract cookies from upgrade headers manually and call the session endpoint.

### `br.user` shape

`br.user` is a discriminated union — check `isLoggedIn` before accessing user properties:

```ts
type BackroadUser = { isLoggedIn: false } | { isLoggedIn: true; name: string; email: string; image?: string; raw: BetterAuthSession };
```

### Approach A: Thin wrapper (recommended)

- User brings their own `betterAuth()` instance, fully configured
- Backroad does nothing but mount the handler and expose `br.user`
- Zero Backroad-owned opinions about which providers or DB to use
- Completeness: 9/10 — ships fast, minimal maintenance surface, full better-auth feature set available

### Approach B: Opinionated wrapper

- Backroad owns the `betterAuth()` config, user passes `providers: ['google']` and a DB string
- More magic, less boilerplate, but Backroad must expose every better-auth option the user might need
- Completeness: 7/10 — more initial work, ongoing maintenance as better-auth evolves

**Recommended: Approach A.** The thin wrapper keeps Backroad's API surface tiny and lets users get the full better-auth experience without Backroad becoming an auth framework.

### Implementation notes

- New optional peer dependency: `better-auth` (not in core bundle)
- Server socket event handler needs to forward session into the script execution context (see WebSocket session flow above)
- No new client-side components needed — developer uses existing `br.button()` / `br.write()` for login UI
- Test coverage: add to Playwright E2E suite (see Feature 3)
- **DB for local dev**: include a minimal SQLite example in `apps/backroad-example` using `better-sqlite3`. This gives users a copy-paste starting point and serves as the test DB for `auth.spec.ts`.
- **Error handling (v1)**: OAuth provider failures result in a redirect back to the app root with an `?error=` query param. No built-in Backroad error UI — developer reads `br.url.searchParams.get('error')` and renders their own message. Document this as a known limitation.

## Feature 2: llms.txt + Copy as Markdown

### What to build

**A. `/llms.txt` at docs site root**

Structure per the llms.txt spec:

```
# Backroad

> A Streamlit-inspired low-code framework for Node.js. Write a script, get an interactive web app.

## Getting Started
- [Introduction](https://backroad.sudomakes.art/docs/fundamentals/introduction/): What Backroad is and how it works
- [Installation](https://backroad.sudomakes.art/docs/fundamentals/installation/): Get up and running in 5 minutes

## Components
- [Write](https://backroad.sudomakes.art/docs/components/write/): Markdown rendering
- [Button](https://backroad.sudomakes.art/docs/components/button/): Interactive button
- [Form](https://backroad.sudomakes.art/docs/components/form/): Input collection
- [File Upload](https://backroad.sudomakes.art/docs/components/file-upload/): File handling
- [LLM](https://backroad.sudomakes.art/docs/components/llm/): Language model integration
... (all components)

## API Reference
- [run()](https://backroad.sudomakes.art/docs/api/run/): Entry point
- [Config](https://backroad.sudomakes.art/docs/api/config/): Configuration options

## Examples
- [Example App](https://github.com/sudomakes/backroad/tree/alpha/apps/backroad-example): Full working example
```

Also provide `/llms-full.txt` — full concatenated docs text for context windows that want everything.

**B. "Copy as Markdown" button on each docs page**

A small button (top-right of each docs page content area) that copies the page's content as clean Markdown to the clipboard — stripping navigation, headers/footers, and HTML cruft.

Implementation options depending on the docs site stack:

- If using Mintlify: already supported natively (`.md` URL suffix + built-in button)
- If using Docusaurus: `docusaurus-plugin-llms` community plugin handles llms.txt; copy button is a custom component
- If custom: copy button strips `nav`, `header`, `footer`, `aside` from the DOM, then converts the remaining `main`/article content to Markdown using `turndown` (preserving `code` blocks and inline code verbatim). Button renders top-right of the content area.

`llms-full.txt` should be generated at build time — a build script concatenates all individual page Markdown files in order. Not a cron job; generated on deploy.

### What to check first

Identify the docs site tech stack (`backroad.sudomakes.art/docs`) before implementing — the approach changes significantly based on whether it's Mintlify, Docusaurus, or custom.

### Framing for the docs / README

> **For AI tooling users:** Paste `https://backroad.sudomakes.art/llms.txt` into Cursor Rules, Claude Projects, or any AI assistant to give it full context about Backroad's API. Use the "Copy as Markdown" button on any docs page to grab a single page's content.

## Feature 3: Playwright E2E

### Goal

The example app (`apps/backroad-example`) serves as both:

1. A live showcase of all Backroad components
2. The E2E test harness that verifies Backroad works end-to-end

### Example app improvements needed

Currently covers: file upload, page routing, LLM chat, button, write/markdown.

Gaps to fill (from `future-goals.md` + component inventory):

- Form inputs (text, number, select, checkbox)
- Table / data display
- Stats / metric components
- Charts
- Column layout
- Auth flow (once Feature 1 ships)

Each gap should have a dedicated route in the example app (already follows the `br.page({ path: '/...' })` pattern).

### Playwright setup

```ts
// playwright.config.ts
import { defineConfig } from '@playwright/test';

export default defineConfig({
  testDir: './e2e',
  use: { baseURL: 'http://localhost:3001' },
  webServer: {
    command: 'pnpm --filter backroad-example run dev',
    url: 'http://localhost:3001',
    reuseExistingServer: !process.env.CI,
  },
  projects: [
    { name: 'setup', testMatch: /global\.setup\.ts/ },
    {
      name: 'e2e',
      dependencies: ['setup'],
      use: {
        /* browser options */
      },
    },
  ],
});
```

### Test structure

```
e2e/
  global.setup.ts       # any one-time setup (seed state if needed)
  components/
    button.spec.ts
    form.spec.ts
    file-upload.spec.ts
    llm.spec.ts
    table.spec.ts
    stats.spec.ts
    charts.spec.ts
    columns.spec.ts
    markdown.spec.ts
  routing.spec.ts        # multi-page navigation
  websocket.spec.ts      # WS connection, reconnect, message flow
  auth.spec.ts           # login/logout flow (gated on Feature 1)
```

### WebSocket testing

Playwright's `page.routeWebSocket()` and `page.waitForEvent('websocket')` give first-class WS support. Key scenarios:

- Verify WS connects on page load
- Verify component state updates are reflected in the browser after a WS message
- Test reconnect behavior (simulate disconnect)

### CI integration

Add to existing GitHub Actions workflow:

```yaml
- name: Install Playwright browsers
  run: pnpm exec playwright install --with-deps chromium

- name: Run E2E tests
  run: pnpm exec playwright test
  env:
    CI: true
```

Playwright runs tests in parallel by default (workers = CPU cores / 2 in CI). Expected suite duration: ~2–4 minutes for ~10 spec files on a standard GitHub Actions runner. Set `timeout: 30000` per test (30s) to catch hung WS connections early.

### Approach A: webServer fixture (recommended)

- Start the actual Backroad dev server in Playwright's `webServer` config
- Tests drive a real browser against a real server
- Completeness: 9/10 — tests real behavior including WebSocket lifecycle

### Approach B: Mock WebSocket layer

- Intercept WS frames with `routeWebSocket()`, feed canned responses
- Faster tests, but misses real server behavior
- Completeness: 6/10 — useful for edge case testing but not as a primary suite

**Recommended: Approach A as primary**, with `routeWebSocket()` used selectively for edge cases (error states, timeouts) that are hard to trigger against a real server.

## Implementation Sequencing

All three features ship as **parallel PRs** — they touch different parts of the codebase with minimal overlap.

| Feature        | Touches                                                                               | Risk                                               |
| -------------- | ------------------------------------------------------------------------------------- | -------------------------------------------------- |
| Auth           | `libs/backroad-core/server`, `libs/backroad/src/lib/backroad`, `libs/backroad-client` | Medium — new server middleware, session forwarding |
| llms.txt       | Docs site only                                                                        | Low — no code changes                              |
| Playwright E2E | `apps/backroad-example`, new `e2e/` directory, `playwright.config.ts`                 | Low — additive only                                |

The only dependency: `auth.spec.ts` in the E2E suite should be written last (after the auth PR lands). Everything else is independent.

## Open Questions

1. **Auth DB requirement**: better-auth requires a database adapter. Should the docs recommend a specific default (SQLite via `better-sqlite3` for local dev)? Or leave it entirely to the user?
2. **Docs site stack**: What is `backroad.sudomakes.art` built with? This determines how much work the llms.txt + copy-as-markdown feature is.
3. **better-auth session in WebSocket context**: Backroad is WebSocket-based, not request/response. The session needs to be resolved from the HTTP upgrade request (the initial WS handshake) and persisted for the lifetime of the connection. Need to verify better-auth's `getSession()` works with the WS upgrade request headers.
4. **`br.user` reactivity**: If a user logs in or out in one browser tab, does the Backroad script re-run in other tabs? Probably not in v1 — document this limitation.

## Success Criteria

- **Auth**: A developer can add `config.auth.instance = betterAuth(...)` to their `run()` call, use `br.user.isLoggedIn` in their script, and have working OAuth (Google at minimum) with zero additional server setup
- **llms.txt**: `https://backroad.sudomakes.art/llms.txt` exists, is valid per the spec, and is mentioned in the README. Every docs page has a "Copy as Markdown" button.
- **Playwright E2E**: `pnpm exec playwright test` passes in CI. Example app covers all core components. Test run is visible in GitHub Actions summary.
